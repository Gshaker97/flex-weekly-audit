This three-file follow-on is separate from frozen release `cd4c0baa714a233467bdace8e54eb0c2691ab4bb`. It adds only a pure bounded planner, tests and this note. It does not change the release, query providers, initialize clients, reserve rows, send, apply fees, suspend service, reactivate workflows, migrate or deploy.

## Implemented now

`planNotificationWorklist(invoices, now)` plans up to 1000 supplied invoice rows. Overflow holds the whole input rather than silently truncating it. Its coverage is explicitly `supplied-invoices-only`; it cannot certify that an account scan was complete or mint source/authorization evidence. Every result remains `dispatchEligible:false`.

- Actual issuedDate remains the operational send date. Actual dueDate controls due+N milestones in America/Phoenix. Nothing uses card entry, createdAt, a guessed payment term or a workflow wait. The target remains 09:00. The existing gate's `[09:00,09:15)` boundary is reused for diagnostic timing, not newly authorized. Earlier dates are reconciliation-only; later same-day work is missed/no-catch-up.
- The **inspected GHL contact-tag rule** remains authoritative for branching: an exact fresh, complete, matching contact-tag snapshot containing `irrigation` selects irrigation; verified absence selects the existing other/maintenance branch. No Jobber product taxonomy is required. Missing/stale/mismatched/case-ambiguous snapshots remain unresolved. If both literal maintenance and irrigation labels exist, a diagnostic notes the mixed labels while retaining the actual irrigation-tag rule.
- Both branches retain homeowner Day10/15 and internal Day21. Unknown tag classification does not block those common milestones or add fee requirements to Day10. Maintenance-only Day20/25/30 possibilities remain visible with a specific unresolved-branch hold when classification is unknown.
- Conditional templates remain explicitly unapproved inputs to the later runtime. The planner lists the existing Day15 applied-fee, Day20/25 recurring-policy, and Day30 suspension/collections-policy evidence requirements. It never claims those effects occurred, supplies copy, infers currency or charges anything. Day10 references binding the existing authorization rather than inventing another per-invoice approval requirement.
- Multiple valid Day21 invoices are retained as distinct stable event keys inside **one planned daily Angie digest per account/location/date**. No member is lost to a first/last selection. The digest template remains unresolved, and the approved internal-recipient role is not converted into a guessed contact ID or destination.
- Duplicate/conflicting source rows hold both copies. Customer contact/day collisions preserve all items with an explicit conflict, rather than choosing a winner or merging unapproved customer wording. Paid/void/nonpositive/unknown/invalid-source rows are reported separately, never silently treated as open.

The planner is deliberately not an Event/Evidence factory or dispatcher. Its structural tag snapshot is a trusted reader input, not an authenticated capability. The eventual runtime still needs actual fresh source/identity, recipient/DND, category where applicable, history, standing-scope checks and ledger admission.

## Smallest next practical adapter/orchestration delta

1. **Bounded inventory and genuine multi-invoice source handles.** Add a no-refresh read-only inventory adapter that exhausts the supported Jobber pages, preserves quarantine/omission evidence and returns the exact invoice/owner/status/balance/issued/due rows. It must distinguish complete scans from partial results. Generalize the existing opaque source reader to retain all owner invoices and recheck the selected invoice independently, rather than requiring exactly one invoice and manually pinned totals/dates per pilot file. Build immutable event bindings from those real current reads. New billing cycles must not inherit old invoice identities or reset prior event keys.
2. **Existing contact GET → tag facts.** Extend the trusted contact observation with exact account/location/contact, complete `tags`, original observation/expiry and provenance. The current source adapter discards tags; the DND parser's existing GET is a natural source for this additional projection. Preserve its DND fail-closed behavior, including missing SMS-channel state. No product taxonomy, carrier lookup or extra consent lookup is needed.
3. **Reusable recurring policy composition.** Replace per-invoice CLI configuration with one authenticated, reviewed recurring recipient/content/action scope covering the approved milestones, customer cohort, sender/footer and schedule. Each discovered event is matched against that scope and bound to fresh source evidence. Standing authorization can cover future routine messages; manual customer-by-customer approval is not an inherent requirement. This does not make the presently unapproved conditional copy approved. Unknown currency is currently permitted only for the exact original non-monetary Day10 body; other copy needs actual currency evidence or a separately reviewed exact non-monetary-copy rule, never fake USD.
4. **Conditional fact adapters.** Identify authoritative actual invoice fee/adjustment evidence for the Day15 applied-3% statement, the applicable recurring-fee policy for Day20/25, and actual suspension plus applicable after-Day35 collections policy for Day30. Date, a larger total, a pipeline stage, a tag or the template's own words do not establish these facts. The current invoice source query does not provide them. Missing evidence holds that conditional event, not common Day10 work. Resolving these data bindings is engineering/source work; it is not a demand for fresh user approval on every invoice.
5. **Angie digest admission and history.** The existing ledger has one notification per event and a contact/day uniqueness rule. It cannot truthfully represent an aggregate by inventing an invoice ID or choosing one member. A real digest needs a durable aggregate claim plus every member's logical event claim, committed atomically before one POST; an unknown result consumes the whole attempted bundle. The current history adapter is homeowner/invoice-scoped and assumes one provider ID maps to one event. A digest needs a reviewed many-member correlation/history projection, not duplicated provider mappings that the current reader correctly rejects. This is a later ledger/data-model and template integration change, not a migration performed here. Every member must be freshly rechecked before inclusion; exclusions remain explicit, with no automatic replay of missed members.
6. **Recurring coordinator and hold reporting.** At the configured Arizona target, read the bounded inventory, plan, then independently admit/recheck each current-window event or approved digest through the real source-gated runner. Preserve sender/DND/history versions, final freshness, original ownership, no retry and all current holds. Report missing facts/history conflicts and unknown outcomes. Do not replay missed milestones, infer deleted history is empty, or revive the retired native enrollments. Homeowner contact/day conflicts still need an explicit orchestration policy; this planner neither discards invoices nor assumes approved combined customer copy.

These are bounded implementation/data decisions. Publication, migration and activation remain separate from preparation; no additional user permission is manufactured by this plan. The parent reports the old 24 enrollments retired and workflows Draft/zero active, so this follow-on contains no resume/re-enrollment path.
